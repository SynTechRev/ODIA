## B-11 Substitution: No External Eval Framework

The handoff implied an external eval framework (e.g. RAGAS, deepeval). Both RAGAS and
deepeval have transitive Python 3.14 incompatibilities (numpy C-exts, tokenizers rust
wheels). Following the B-11 substitution pattern: native implementation over stdlib
replaces the framework dependency.

The 7-metric design is derived from the original RAGAS metric set (faithfulness,
answer_relevancy, context_precision, context_recall) adapted to ODIA's anomaly-detection
domain: citation density replaces faithfulness, citation precision replaces
answer_relevancy, and ODIA-specific metrics (iteration_efficiency, answer_adequacy,
category_balance, latency) complete the scorecard.

## Architecture

### 7 Metrics

| Metric | Formula | Threshold | Gate |
|---|---|---|---|
| verify_pass_rate | halt_reason=="verify_passed" / total | 0.75 | gate |
| citation_density_mean | mean(citations/words across traces) | 0.75 | gate |
| citation_precision_mean | mean(valid_doc_citations/total_citations) | 0.80 | gate |
| iteration_efficiency | 1 - (mean_iterations / max_iterations) | 0.40 | gate |
| answer_adequacy | mean(judge.score(query, answer)) | 0.50 | gate |
| category_balance | min_category_count / max_category_count | 0.60 | gate |
| latency_p50_ok | fraction with latency < SLA | 0.0 | informational |

latency_p50_ok has threshold 0.0: it never blocks CI but appears on the scorecard for
trending. Gate semantics: all gate metrics must pass for overall PASS verdict.

### HeuristicJudge

Five-criterion rubric, 0.2 points each:
1. Has at least one `(doc_id:...)` citation pattern
2. Answer length >= 150 characters
3. No boilerplate phrases ("I cannot", "I don't have", etc.)
4. Contains a statute/code reference (CFR, USC, PC, Government Code, etc.)
5. No unreplaced template artifacts (`{answer}`, `{{`, etc.)

Used as the default judge. Deterministic, zero latency, no external dependency.

### OllamaJudge

Calls Ollama REST API (`http://localhost:11434/api/generate`) with the deployed
odia-v2 model. Rubric prompt asks for 0.0-1.0 float response. Falls back to
HeuristicJudge if Ollama is unavailable or returns a non-float response. Safe by
default; degrades gracefully in CI environments where Ollama is not running.

### CI Gate

`EvalHarness.run_from_traces()` returns a `Scorecard` with `gate_passed: bool` and
`verdict: "PASS" | "FAIL"`. The runner script exits 0 on PASS, 1 on FAIL. In CI
(Day 11), the gate blocks the consolidation PR if any gate metric fails.

## iteration_efficiency FAIL: Expected at Day 10

**Why it failed**: The Day 4 RAIA run required 2.0 mean iterations per query against a
3-iteration cap (efficiency = 1 - 2/3 = 0.333). The 0.40 threshold requires mean
iterations <= 1.8 -- i.e., most queries must resolve in 1-2 iterations, not 2-3.

**Why it is expected**: The Day 4 traces were generated by odia-v2 (base QLoRA, no
DPO). The verify node flagged citation gaps on most traces, requiring at least one
reflection loop. This is the exact behavior that DPO training (Day 6) is designed to
address: the preference pairs penalize traces that reach verify with unfilled citations
and reward traces that converge in 1-2 iterations.

**Production gate path**:
1. Vast.ai Day 11: train odia-v3 on Day 6 DPO pairs (5 pairs, forward mode)
2. Deploy odia-v3 to Ollama
3. Re-run `scripts/run_eval_harness.py` against a full 100-query eval set
4. Expected: iteration_efficiency >= 0.40 after DPO (verify passes more often on first
   try)

The Day 10 scorecard is the pre-DPO development baseline. The Day 11 post-DPO
scorecard is the first production gate run.

## Data Lineage for Scorecard Metrics

The harness reads JSONL traces emitted by `agents/raia_v0.py`. Each trace line is a
JSON object with:
- `query`: the question
- `halt_reason`: "verify_passed" | "max_iterations_reached" | null
- `final_answer`: the last deepen_node output
- `trace`: list of {node, ...} dicts counting iterations
- `citations`: list of `(doc_id:...)` strings extracted from final_answer
- `citation_count`, `word_count`, `latency_s`: pre-computed by the runner

The harness is agnostic to trace format version: it reads only these keys and
gracefully handles missing/null values (treats null halt_reason as non-verified,
null answer as empty string).
